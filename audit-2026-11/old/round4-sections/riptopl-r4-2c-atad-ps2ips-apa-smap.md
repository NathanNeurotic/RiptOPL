### R4C-01 — cdvdman `atad.c`: the PIO transfer function returns success before transferring anything; ~45 lines below it are unreachable
- **Category:** 6 (bugs/security) / 1 (dead code) / 8
- **Location:** `modules/iopcore/cdvdman/atad.c` — `ata_pio_transfer` `:470-516`, early exit at `:473-474`; sole caller is the PIO branch of `sceAtaWaitResult` at `:615`.
- **Problem + mechanism (READ):** The function opens with
  > `SPD_REG8(SPD_R_PIO_DATA) = 0;` / `return 0;` (`:473-474`)
  Everything after it — the status/ERR check, the DRQ check, the type-2 PIO-in loop and the type-3/8 PIO-out loops (`:476-516`) — can never execute. `sceAtaWaitResult` routes every non-DMA, non-trivial command type through this function per block (`:615`, `while (--cmd_state->blkcount != -1)`): that includes IDENTIFY DEVICE / IDENTIFY PACKET DEVICE (table type `0x02`, `atad.c:101`) and SMART (type `0x07`). Any such command therefore completes with success while (a) the caller's buffer is never filled (PIO-in) and (b) nothing is ever written to the device (PIO-out). The hdpro sibling's copy of the same function (`hdpro_atad.c`, `ata_pio_transfer`) has **no** such early return and performs the transfer with a checksum — so the two ATAD variants in the same directory disagree about whether PIO works at all.
- **Reachability (READ):** no caller inside `modules/iopcore/cdvdman/` issues a PIO-type command today — `device-hdd.c` uses only `sceAtaDmaTransfer` (DMA types) and `sceAtaFlushCache` (type 1). The defect is therefore latent, not live: it fires the first time any present or future cdvdman code path issues IDENTIFY/SMART through this driver, and it will fail silently (success + stale buffer), the worst failure shape for a probe.
- **Fix (words):** Decide once. If cdvdman is DMA-only by design, delete the dead body of `ata_pio_transfer` and make the PIO branch of `sceAtaWaitResult` return `ATA_RES_ERR_CMD` for types it cannot service, so the refusal is explicit at the call site. If PIO is meant to work, delete the two early-exit lines and let the existing body run (it is complete and mirrors hdpro's). Do not keep a success-returning stub over a full implementation.
- **Benefit:** Removes a silent-success trap from the in-game ATA driver and ~45 lines of review surface (deletion branch), or restores IDENTIFY/SMART (repair branch).
- **Effort:** S · **Risk:** Low for the deletion branch (no live caller changes behaviour); Medium for the repair branch (PIO timing on real hardware would need a bench pass — not attempted here) · **Confidence:** READ (deadness and inter-variant divergence); INFERRED (whether the stub was deliberate — the tree records no reason).

### R4C-03 — `hdpro_atad.c`: `sceAtaDmaTransfer` retries a failing chunk forever, with no delay, while holding the I/O semaphore
- **Category:** 6 (bugs/security) / 5
- **Location:** `modules/iopcore/cdvdman/hdpro_atad.c` — transfer loop `:692-720`; the retry is explicit at `:714` (`//Unlike ATAD, retry indefinitely until the I/O operation succeeds.`) with bare `continue` at `:717` and `:719`. Semaphore taken at `:688` (`WAITIOSEMA(ata_io_sema)`), released only after the loop.
- **Problem + mechanism (READ):** On **any** error from `sceAtaExecCmd` or `sceAtaWaitResult` — not only transient CRC errors — the same chunk is re-issued immediately, forever. There is no retry cap, no back-off (`DelayThread` never appears in the loop), and no error-class filter. A permanent failure — failing/removed disk, wedged HDPro bridge, a command the drive persistently rejects — therefore spins the calling IOP thread at full speed re-programming the HDPro registers, and because `ata_io_sema` is held for the whole transfer, every other ATA user (including the shutdown flush path) blocks behind it permanently. The game does not get an error it could react to; the console wedges. The sibling driver shows the intended shape: `atad.c:700-…` retries at most 3 times and only while the error is `ATA_RES_ERR_ICRC`, then returns the error with the semaphore released.
- **Fix (words):** Bound the retry like the sibling: retry only on the transient error class, at most a small fixed number of times, with a short delay between attempts; return the final error (and release the semaphore, as the post-loop code already does) when the budget is spent. This is a change to existing lines, nothing added.
- **Benefit:** A dead disk on HDPro hardware becomes a returned `-EIO`-class failure instead of a permanent, semaphore-holding console wedge.
- **Effort:** S · **Risk:** Low–Medium (changes HDPro error behaviour from "hang" to "fail"; any caller secretly depending on infinite retry was depending on a hang) · **Confidence:** READ.

### R4C-04 — `ps2ips.c`: `do_setsockopt` copies an EE-supplied length into a 128-byte stack buffer with no bound
- **Category:** 6 (bugs/security)
- **Location:** `modules/network/ps2ips/ps2ips.c` — `do_setsockopt` `:583-596`; the copy is `memcpy(optval, ((setsockopt_pkt*)rpcBuffer)->buffer, optlen);` at `:592`, with `optlen` taken unchecked from the RPC packet at `:591` and `unsigned char optval[128]` at `:587`.
- **Problem + mechanism (READ):** `optlen` is a field of the EE→IOP RPC request. Nothing clamps it to 128 (or to the request buffer's own payload size) before the `memcpy`, so a request with `optlen > 128` overwrites the RPC thread's stack past `optval` — return address and neighbouring locals — by an attacker-/bug-controlled amount, on a thread whose stack is 0x800 bytes (`_start`, `t.stacksize = 0x800` at `:738`). The caller is the console's own EE code, so this is a robustness/integrity hole rather than a remote exploit; it still converts any EE-side bug (or a corrupted RPC buffer) into IOP memory corruption inside the network stack. The file's own project notes already record this exact defect as seen-but-unfixed (`docs/PS2SDK-NOTES.md`, §ps2ips "Seen in ps2ips, not changed here"); it has never carried a RiptOPL finding ID.
- **Fix (words):** Refuse the call when `optlen` exceeds `sizeof(optval)` (return an error in `ptr[0]`, as the function's other results are returned), before the copy. One comparison; nothing added.
- **Benefit:** Closes the only unbounded EE→IOP copy left in the RPC server; the rest of the file's receive path was already hardened to this standard (see the verdict table).
- **Effort:** S · **Risk:** Low (no legitimate sockopt value for the options lwIP supports approaches 128 bytes) · **Confidence:** READ.

### R4C-05 — `ps2ips.c`: `do_accept` / `do_getsockname` / `do_getpeername` pass an uninitialised `addrlen`, and copy the address struct to the reply even when the call failed
- **Category:** 6 (bugs/security)
- **Locations:** `modules/network/ps2ips/ps2ips.c` — `do_accept` (`int addrlen` declared `:92`, passed to `accept()` uninitialised; reply `memcpy(&pkt->sockaddr, &addr, sizeof(struct sockaddr))` unconditional), `do_getsockname` (same shape, `addrlen` at `:531`), `do_getpeername` (same shape, `addrlen` at `:547`); contrast `do_recvfrom`, where the identical parameter **was** fixed (`int fromlen = sizeof(struct sockaddr);` at `:289`, with an "RA fix" comment explaining lwIP copies only `min(*fromlen, 16)` bytes).
- **Problem + mechanism (READ):** (a) lwIP treats `addrlen` as value-result: an uninitialised stack value below 16 truncates the copied address, and 0 copies none — the EE then receives a zeroed or partial sockaddr while the return value reports success. This is the same defect class the file already fixed in `do_recvfrom` and documents there; the three sibling handlers were left unfixed. (b) All three copy the local `struct sockaddr addr` into the reply packet **regardless of the call's return value**; on failure `addr` is untouched stack memory, so uninitialised IOP stack bytes are returned to the EE as if they were an address. Also already recorded as seen-but-unfixed in `docs/PS2SDK-NOTES.md` §ps2ips; no prior finding ID.
- **Fix (words):** Initialise each `addrlen` to `sizeof(struct sockaddr)` before the call (the `do_recvfrom` line, copied), and only copy `addr` into the reply when the call returned success. Three small edits reusing the file's own fixed pattern.
- **Benefit:** Accepted/queried peer addresses stop being intermittently zeroed, and a failed call stops leaking stack contents into an EE-visible struct.
- **Effort:** S · **Risk:** Low · **Confidence:** READ (lwIP's `min(*fromlen,16)` copy behaviour is as documented in the file's own `do_recvfrom` comment and the project notes).

### R4C-06 — `ps2ips.c`: `do_getsockopt` always copies 128 bytes into the reply, whatever the call actually returned
- **Category:** 6 (bugs/security, minor)
- **Location:** `modules/network/ps2ips/ps2ips.c` — `do_getsockopt` `:560-575`; `memcpy(((getsockopt_res_pkt*)rpcBuffer)->buffer, optval, 128);` at `:574`.
- **Problem + mechanism (READ):** The local `optval[128]` is filled by `getsockopt(..., &optlen)` with `optlen` initialised to `sizeof(optval)` at `:568`. The reply copy ignores both the return value and the resulting `optlen`: on failure, or for any option shorter than 128 bytes (in practice all of them), the tail of the EE-visible reply buffer is whatever was on the RPC thread's stack. The reply's own `optlen` field is set correctly (`:573`), so a correct EE caller reads only `optlen` bytes — impact is limited to stack-byte disclosure into a buffer the EE owns, plus a trap for any caller that trusts the full 128. Filed because the sibling defect in the same function pair (R4C-04) is a genuine overflow; this one is its low-grade mirror.
- **Fix (words):** Copy only the returned `optlen` bytes on success (and zero or omit the buffer on failure). One line changed.
- **Benefit:** Reply contents become exactly what the syscall produced.
- **Effort:** S · **Risk:** Low · **Confidence:** READ.

### R4C-07 — `apa.c`: `apaFindPartition` converts a chain-walk I/O error into a clean "not found" — and one live caller then returns success with an unfilled stat
- **Category:** 6 (bugs/security)
- **Location:** `modules/hdd/apa/src/apa.c` — `apaFindPartition` `:170-193`; the masking lines are the tail: on walk error (`*err != 0` after the loop) it executes `*err = 0; return NULL;`. Live caller (READ): `modules/hdd/apa/src/hdd_fio.c` `hddGetStat` at `:782-789`.
- **Problem + mechanism (READ):** The walk distinguishes two exits internally — header chain ended cleanly (`*err == 0` → it sets `*err = -ENOENT`) versus a header read failed mid-chain (`apaCacheGetHeader` set `*err`, e.g. `-EIO`) — and then deliberately erases the second: `*err` is reset to 0 and NULL returned either way. Callers therefore cannot distinguish "partition does not exist" from "the disk stopped answering". In `hddGetStat` the consequence is concrete: it tests only the returned pointer, skips the password/stat fill, and `return rv;` with `rv == 0` — **getstat reports success and leaves the caller's stat struct unfilled**. Other callers (mostly the refused partition-edit paths, RIPTOPL-052) inherit the same confusion at lower stakes.
- **Fix (words):** Delete the error-erasing tail: when the walk ends with `*err != 0`, return NULL **with `*err` intact**; keep the `-ENOENT` assignment only for the clean-end case. No caller needs a new branch — `hddGetStat` already propagates `rv`.
- **Benefit:** Disk failures surface as errors instead of phantom success/ENOENT; one branch removed, none added.
- **Effort:** S · **Risk:** Low (callers that ignored `rv` on NULL still get NULL) · **Confidence:** READ.

### R4C-08 — `apa.c`: `apaGetFormat` dereferences an unchecked cache allocation
- **Category:** 6 (bugs/security)
- **Location:** `modules/hdd/apa/src/apa.c` — `apaGetFormat` `:461-…`, allocation at `:467` (`clink = apaCacheAlloc();` followed immediately by `apaReadHeader(device, clink->header, 0)`). Contrast the same file's `apaGetPartErrorSector` at `:58`, which checks the identical call (`if (!(clink = apaCacheAlloc())) return -ENOMEM;`).
- **Problem + mechanism (READ):** `apaCacheAlloc` returns NULL when the cache pool is exhausted (its contract is demonstrated by the checked call site at `:58` and by `cache.c`). `apaGetFormat` passes `clink->header` to `apaReadHeader` — which DMA-reads into it — with no NULL test, so cache exhaustion turns a format probe into a NULL-pointer DMA write + crash on the IOP. The function is live: it is called from `modules/hdd/apa/src/hdd.c:331` and `modules/hdd/apa/src/hdd_blkio.c:126,263` during device probing (READ).
- **Fix (words):** Copy the guard the same file already uses at `:58`: if the allocation fails, set `*format = 0` (already done before the call) and return `-ENOMEM` before touching `clink`.
- **Benefit:** A probed-under-pressure driver fails the probe instead of crashing the IOP.
- **Effort:** S · **Risk:** Low · **Confidence:** READ.

### R4C-10 — `udpfs_ioman.c`: open handles keep their pre-disconnect server handle numbers across a watchdog reconnect
- **Category:** 6 (bugs/security)
- **Location:** `modules/network/udpfs_ioman/src/udpfs_ioman.c` — handle table `:41-47` (`g_fds[8]`), validation `:66-80` (`_validate_fd`), watchdog `:98-107`.
- **Problem + mechanism:** The watchdog heals a dropped session by calling `udpfs_core_init()` whenever `udpfs_core_is_connected()` goes false (`:102-104`). Nothing in that transition touches `g_fds`: slots keep the `server_handle` integers issued by the **old** server session. `_validate_fd` checks only that the session is currently connected and the local slot is occupied (`:70-76`) — there is no session generation or epoch anywhere in the file (grep, READ). After a heal, the next read/write/lseek on a still-open file sends the stale integer to the new session. What the server does with it is server-side (INFERRED): at best an error; at worst, if the new session has already issued the same small integer for a different file, the operation lands on the wrong file. The window is realistic — the watchdog exists precisely because servers are hand-started, restarted, and time out mid-use (file comment `:88-97`).
- **Fix (words):** Invalidate the table at the moment the watchdog observes the disconnected state (mark every slot free before re-initialising the core), so post-heal operations fail with `-EBADF`/`-EIO` and the EE re-opens, instead of silently reusing numbers from a dead session. A deletion-shaped change: the invalidation is a loop the file already has at init (`:128-130`).
- **Benefit:** A server restart can no longer alias an open OPL file handle onto an unrelated server-side file.
- **Effort:** S · **Risk:** Low (files open across a disconnect are unusable in practice today; this makes that explicit instead of accidental) · **Confidence:** READ for the missing invalidation in this file; INFERRED for the wrong-file outcome (depends on the server's per-session handle allocation, audited in the PS2-Servers rounds, not here).

### R4C-12 — SMAP: the DEV9 capability check is a no-op in both neutrino copies (operator precedence); the ingame copy has the correct form
- **Category:** 6 (bugs/security) / 2 (drift)
- **Locations:** `modules/network/udpfs_smap/src/smap.c:516` and `modules/network/smap_udpbd/src/smap.c:522` — both read `if (!SPD_REG16(SPD_R_REV_3) & SPD_CAPS_SMAP) return -1;`. Correct form in-tree: `modules/network/smap-ingame/smap.c:541` — `if ((SPD_REG16(SPD_R_REV_3) & SPD_CAPS_SMAP) == 0) return -1;` (the same idiom, correctly parenthesised, at `modules/hdd/atad/src/ps2atad.c:282` and `modules/iopcore/cdvdman/atad.c:197`).
- **Problem + mechanism (READ):** In C, `!` binds tighter than `&`, so the expression parses as `(!SPD_REG16(...)) & SPD_CAPS_SMAP`. `!x` is only ever 0 or 1, so the whole condition can be nonzero only when the register is exactly 0 **and** the capability mask has bit 0 set. For any normal nonzero revision register the check evaluates to 0 and never fires: both drivers proceed to reset FIFOs, program the EMAC and register interrupt handlers on hardware where the SMAP capability may be absent (e.g. a DEV9 variant without Ethernet), instead of failing init with `-1` as intended. The exact value of `SPD_CAPS_SMAP` lives in the PS2SDK `speedregs.h` (not in this repo), so the "only bit 0 could ever fire it" statement is READ from C precedence; whether it can fire at all on real register values is INFERRED.
- **Fix (words):** Parenthesise both copies to the ingame form — test `(register & SPD_CAPS_SMAP) == 0`. Two one-line edits; if R4C-11's merge happens first, one.
- **Benefit:** Init fails cleanly on SMAP-less DEV9 hardware instead of programming a non-existent EMAC.
- **Effort:** S · **Risk:** Low (on any hardware where SMAP works today the bit is set and behaviour is unchanged) · **Confidence:** READ (precedence and the in-tree correct forms); INFERRED (real-world register values).

### R4C-13 — SMAP: in both neutrino copies `HandleRxIntr` never counts a packet, so the link-check suppression both `smap.c` copies implement is dead
- **Category:** 6 (bugs/security) / 2 (drift)
- **Locations:** `modules/network/udpfs_smap/src/xfer.c` — `NumPacketsReceived` declared `:162`, zeroed `:169`, returned `:203`, **never incremented** (grep-complete for the file, READ); identical shape in `modules/network/smap_udpbd/src/xfer.c` (`:111`, `:119`, `:151`). Consumers: `modules/network/udpfs_smap/src/smap.c:431` and `modules/network/smap_udpbd/src/smap.c:437` — `ResetCounterFlag = HandleRxIntr(...)`, with the stated intent at `udpfs_smap/src/smap.c:442-446` ("Do the link check, only if there has not been any incoming traffic in a while": a nonzero return resets the 3-strike counter and skips the check). Contrast: `modules/network/smap-ingame/xfer.c:212` does `NumPacketsReceived++;` (ingame's `smap.c` discards the return and polls the link unconditionally on a 5 s alarm — a coherent, different design).
- **Problem + mechanism (READ):** Because the return is permanently 0, `ResetCounterFlag` is permanently false and the 3-strike counter decrements on every 1-second link-check event regardless of traffic: `CheckLinkStatus` runs roughly every 3 seconds even mid-transfer. `CheckLinkStatus` itself is guarded — it only re-runs `InitPHY` when the BMSR link bit reads clear — so the standing cost is a PHY register read every ~3 s (negligible); the hazard is the tail case (INFERRED): a transient BMSR clear under load triggers a full PHY re-initialisation in the middle of active UDPFS/UDPBD traffic, in exactly the situation the counter was designed to prevent.
- **Fix (words):** Increment the counter once per processed frame in both `xfer.c` copies (the ingame line, in the neutrino loops' frame-processed position), or — if the suppression is not wanted — delete `ResetCounterFlag` and the counter logic from both `smap.c` copies and poll unconditionally like ingame. Either way the two halves must agree; today they describe a mechanism that does not exist.
- **Benefit:** The documented traffic-aware link check either works or stops pretending to; removes a mid-transfer PHY-reset tail risk.
- **Effort:** S · **Risk:** Low · **Confidence:** READ (counter never incremented; consumer logic); INFERRED (transient-BMSR consequence).
