## Candidate findings

### R4-1a-01 — VCD scan allocates the 2,048-entry cap (~532 KB) for every folder, however small
- Category: 4 (size/memory)
- Location: `src/sources/vcdsupport.cpp:653` READ; second full-size copy at `:1037` READ
- Problem: `vcd_entry_t *list = (vcd_entry_t *)calloc(VCD_MAX_ITEMS, sizeof(vcd_entry_t));` allocates 2048 × 260 B = **532,480 B unconditionally** at the start of every `vcdScanOpenDir`, whether the POPS folder holds 2 games or 2,000. The list is then walked and, in `vcdFillGameList` (`:1037`), copied into a second allocation `memalign(64, n * sizeof(base_game_info_t))` (up to another ~385 KB at the cap) before the first is freed — so peak transient heap for one scan approaches ~0.9 MB on a 32 MB EE, for a data set whose common case is tens of entries (~5 KB). The cap is a correctness bound, not a working-set estimate; nothing in the function needs random access to unwritten slots.
- Fix (words): grow the array instead of pre-sizing it — start at a small capacity (e.g. 64 entries) and double with `realloc` when `count` reaches capacity, failing the scan (-1, preserving the caller's list, exactly as the current OOM branch does) if a grow fails. No other logic changes; the existing `count < VCD_MAX_ITEMS` loop condition stays as the hard cap.
- Justification if ADD: adds only the capacity variable and the grow branch inside code that already exists; removes a fixed half-megabyte reservation. Net win on the scarcest resource in the system.
- Benefit: per-scan heap peak drops from ~532 KB (+ copy) to roughly the real library size; removes the largest single transient allocation on the list-build path.
- Effort: S–M. Risk: Low (one function, existing OOM semantics reused; `realloc` failure must free the old block and return -1, mirroring the `calloc == NULL` branch). Confidence: READ (allocation size is arithmetic from header constants in front of me).

### R4-1a-02 — The only two unbounded `sprintf` calls left in either file build the `games.bin` path into a 256-byte stack buffer
- Category: 6 (bugs/security)
- Location: `src/sources/supportbase.cpp:177` and `src/sources/supportbase.cpp:269` READ
- Problem: `loadISOGameListCache` and `updateISOGameList` each declare `char filename[256];` and fill it with `sprintf(filename, "%s/games.bin", path);`. A repo-wide grep confirms these are the **only** `sprintf` (unbounded) calls in either audited file — everything else uses `snprintf`. `path` arrives from `sbReadList`, which composes it into its own `char path[256]` with `snprintf` (`"%sCD"` / `"%sDVD"` / subpath forms), so `path` can legitimately be up to 255 chars; appending `"/games.bin"` (10 chars + NUL) then writes up to ~10 bytes past `filename` on the stack. Today's device prefixes are short, so this is latent, not live — but it is exactly the class the rest of the file has been systematically cleaned of, and a longer prefix/subpath combination is the only trigger needed.
- Fix (words): change both `sprintf` calls to `snprintf(filename, sizeof(filename), "%s/games.bin", path)` and treat a truncated result the same way neighbouring code treats other truncated paths (the cache load already returns `ENOENT`-style failure / the update already tolerates `EIO`-style failure). Two-word change per site, no new code.
- Justification if ADD: none needed — pure replacement, strictly less.
- Benefit: removes the last unbounded string copy in 6,440 audited lines; cache path can fail closed instead of corrupting the stack.
- Effort: S. Risk: Low (a truncated path simply misses the cache, the already-handled case). Confidence: READ for the mechanism and buffer arithmetic; INFERRED (low impact today) for reachability, because current prefixes are short.

### R4-1a-07 — VCD scan is quadratic twice: per-entry cue dedup scans + per-entry linear memo walk
- Category: 5 (performance, structural)
- Location: `src/sources/vcdsupport.cpp:695-715` (cue/VCD dedup) with `noteScanDir` → `idMemoFind` at `:308-315` / `:317-345`, called per entry at `:716` READ
- Problem: two nested-loop costs multiply the scan's readdir loop. (a) UDPFS cue handling: each `.cue` row linear-scans all previously kept rows (`for (int k = 0; k < count && !dup; k++) dup = !strcmp(...)`), and each subsequent `.VCD` row does the same scan again while `cueCount > 0` — O(n²) string compares over up to `VCD_MAX_ITEMS` = 2,048 rows. (b) Independently, **every** scanned entry (all devices, not just UDPFS) calls `gVcdSupport.noteScanDir(...)`, whose first act is `idMemoFind` — a linear `strcmp` walk of the session memo, which grows to its 512-entry cap (`VCD_ID_MEMO_MAX`) as the scan proceeds. A full folder therefore costs on the order of 2,048 × ~256 average memo probes ≈ 500k `strcmp`s of bookkeeping on top of the directory read, on the IO worker that also serves artwork and BGM. Neither loop is bounded by anything small.
- Fix (words): (a) do the cue/VCD twin suppression once, after collection — the entries are already `qsort`ed when `gAutosort` is on; where it is off, sort a throwaway copy of the name order for dedup only, then keep first occurrences adjacently. That deletes both inner scans. (b) for the memo, keep the list but note scan directories in bulk: `noteScanDir` is handed the same `dirPath` for every row of one scan, so resolve/create the memo entries with the directory string compared once per *new* name only — or, simpler and smaller, cap the walk's cost by inserting new entries at the head (already done) and accepting the walk only for names not yet memoised is not a fix; the honest LESS fix is (a) plus: skip the memo walk entirely for names already known to belong to this same `dirPath` by caching the last (name,kind) miss pattern is fragile — prefer: build the scan's memo notes into a temporary array and merge once. If (b)'s merge is judged too much new code, ship (a) alone and record (b) as accepted: the memo cap (512) bounds it, the scan does not.
- Justification if ADD: (a) adds no persistent structure — it reuses the sort the file already performs. (b) is explicitly conditional above; no new subsystem proposed.
- Benefit: scan cost returns to ~O(n log n); large POPS folders (the 2,048 cap exists because they occur) stop paying quadratic bookkeeping on every refresh.
- Effort: M. Risk: Medium for (a) — twin-suppression semantics ("a real .VCD wins", cue pair counts once) must be preserved exactly in the post-sort pass, including when `gAutosort` is off. Confidence: READ for the loop structure and bounds; INFERRED for real-world impact (no profiling possible here; typical folders are far below the cap).

### R4-1a-08 — `vcdIsHiddenDisc` accumulates an unbounded disc number into an `int` — signed overflow from a crafted filename
- Category: 6 (bugs/security)
- Location: `src/sources/vcdsupport.cpp:990-1011`, accumulation at `:1007` READ
- Problem: for each "(disc"/"[cd"/"(disk" token, the code runs `int num = 0; while (*d >= '0' && *d <= '9') num = num * 10 + (*d++ - '0'); if (num >= 2) return 1;`. The digit run is bounded only by the filename length, and names reaching this function come from the scan (basename cap `ISO_GAME_NAME_MAX` = 160 chars) — a file named e.g. `Game (Disc 99999999999999999999).VCD` (a 20-digit run, well inside 160 chars) overflows a signed 32-bit `int` mid-loop: undefined behaviour, and the wrapped value can land below 2, misclassifying a disc-2+ file as disc 1 (or vice-versa depending on wrap). The input is filesystem-supplied — precisely the untrusted side of this parser.
- Fix (words): return 1 the moment `num` first reaches ≥ 2 inside the digit loop. That is exact, not approximate: appending further decimal digits to a value already ≥ 2 can only increase it (`num*10 + d ≥ num` for `num ≥ 0`), so no later digit can change the answer — and `num` then never exceeds 29. Deletes the overflow and shortens the common multi-disc scan.
- Justification if ADD: none — the fix removes work.
- Benefit: removes a signed-overflow UB on untrusted filenames; multi-disc detection gets marginally faster.
- Effort: S. Risk: None (monotonicity argument above). Confidence: READ.

### R4-1a-10 — The IPCONFIG.DAT triple is implemented three times in one file, with two parsers of different strictness for the same format
- Category: 2 (duplication) + 6 (parsing consistency)
- Location: `src/sources/vcdsupport.cpp:2471-2478` (`vcdParseIpConfig`, sscanf), `:2118-2145` (`vcdUdpfsParseQuad`, strict), `:2796-2802` (`vcdBuildIpConfig`), `:2279-2282` (UDPFS writer's inline snprintf of the same format) READ
- Problem: the `"<IP> <MASK> <GW>"` line exists as: a lax parser (`sscanf(buf, "%d.%d.%d.%d %d.%d.%d.%d %d.%d.%d.%d", ...)` + a 0–255 range check), a strict parser (`vcdUdpfsParseQuad`: digit-by-digit, rejects an octet the moment it passes 255, requires a delimiter or end after the last octet), and two separate serializers (`vcdBuildIpConfig` for `vcd_popsnet_t`, an open-coded identical `snprintf` in `vcdWritePopsUdpfsNet` for `vcd_pops_udpfs_t`). The two parsers disagree on real inputs: the sscanf form accepts trailing junk after the final octet (its last `%d` happily parses `4` out of `4xyz` and still returns 12 conversions) and accepts embedded junk the strict form rejects, so a file the POPSTARTER-net editor calls valid can be one the UDPFS-net editor calls invalid and vice-versa — for files in the same format family, read by the same external program. `%d` conversion of an over-long digit string in `sscanf` is also implementation-defined/undefined territory the strict parser was clearly written to avoid — for the *other* struct.
- Fix (words): delete `vcdParseIpConfig`'s sscanf body and implement it on top of `vcdUdpfsParseQuad` (skip-space, parse quad, three times — the UDPFS reader at `:2295-2315` already shows the exact pattern), so both net editors share one strictness. Leave the two serializers: they write two different structs, and merging them would need a common struct or an adapter — that would be MORE, not less.
- Justification if ADD: none — one parser replaces the other; net lines decrease.
- Benefit: one definition of a valid IPCONFIG line; removes the sscanf-overflow surface from this file entirely.
- Effort: S–M. Risk: Low-medium — files previously accepted only by the lax parser (trailing junk) become "invalid" in the editor, which is the repair-don't-shadow behaviour the surrounding home-resolution code already prefers; POPSTARTER's own tolerance is out of scope and unchanged on disk. Confidence: READ for the duplication and the sscanf acceptance mechanism; INFERRED for how many real-world files sit in the disagreement gap (expected: ~none).
