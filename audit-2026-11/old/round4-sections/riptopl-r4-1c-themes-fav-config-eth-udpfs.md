## New findings

### S-01 — Theme catalog entry allocations are used without a NULL check
- **Category:** 6 (bugs/security)
- **Location:** `src/gfx/themes.cpp:1045` (`currTheme->name = (char *)malloc(length + 1);` followed immediately by `memcpy(currTheme->name, name + 4, length);`) and `src/gfx/themes.cpp:1050-1051` (`currTheme->filePath = (char *)malloc(length * sizeof(char));` followed by `sprintf(currTheme->filePath, "%s%s%s%s", path, separator, name, separator);`)
- **Problem + mechanism:** `ThemeCatalog::readEntry` runs for every `thm_`-prefixed directory/archive entry on every device scan. Both allocations are dereferenced on the next line with no NULL check. On an EE that is already carrying a fully built theme, textures and game lists, a failed small malloc during a theme scan (a second device coming up is exactly when memory is tightest) is not a graceful "theme skipped" — it is a write through NULL from `memcpy`/`sprintf`, crashing the loader during device enumeration. Every other allocation site touched in this same round's files checks: `favStrdup`, `favBuildImage`, `thmLoad`'s own `newT` malloc at the top of the function, and `cloneImageCache`'s caller all handle NULL; this pair does not.
- **Fix (words):** Check both allocations; on failure, free the first if it succeeded, leave the slot unused and return `index` unchanged (the theme is simply not listed, exactly as a non-directory candidate is not listed).
- **Benefit:** A theme scan under memory pressure degrades to a missing theme instead of a crash.
- **Effort:** S · **Risk:** Low · **Confidence:** READ

### S-02 — `thmGetTexture` dereferences `gTheme` with no NULL guard
- **Category:** 6 (bugs/security)
- **Location:** `src/gfx/themes.cpp:938-951` — `GSTEXTURE *txt = &gTheme->textures[id];` after only the `id >= TEXTURES_COUNT` check.
- **Problem + mechanism:** `gTheme` is NULL before the first `thmLoad` (thmInit sets it NULL, then loads) and the file's own sibling accessors all guard (`thmGlyphSetRefresh`, `thmRefreshFontSize`, `thmSetViewLocked`, `isDecoratorCoverImage` each test `gTheme`/`theme` for NULL first). `thmGetTexture` is the one public accessor that does not. Any draw-path caller that runs before the first successful load — or after a load was abandoned in the window before a theme exists — dereferences NULL instead of receiving the NULL this function already returns for an invalid/unloaded texture, which is plainly its intended contract (`txt->Mem` NULL → NULL).
- **Fix (words):** Return NULL when `gTheme == NULL`, alongside the existing range check.
- **Benefit:** The texture accessor honours its own "NULL means nothing to draw" contract in the pre-load window.
- **Effort:** S · **Risk:** Low · **Confidence:** READ (that a caller actually reaches it pre-load today is INFERRED — the defect is the missing guard in a function whose contract is to answer NULL)

### S-03 — `thmLoadResource`'s `psm` parameter is dead: accepted at ~10 call sites, never used
- **Category:** 1 (dead code)
- **Location:** `src/gfx/themes.cpp:1061` — `static int thmLoadResource(GSTEXTURE *texture, int texId, const char *themePath, short psm, int useDefault)`; the body (`:1063-1074`) calls only `texDiscoverLoad(texture, themePath, texId)` and `texLoadInternal(texture, texId)`, neither of which takes a pixel format.
- **Problem + mechanism:** Every caller passes `GS_PSM_CT32`, which reads as "this load honours a pixel format" and honours nothing. A future caller passing a different psm for a palette/CLUT texture would silently get CT32 behaviour. This is the same false-affordance shape as a dead config key: the parameter costs a register/stack slot per call and, worse, a reader's trust.
- **Fix (words):** Delete the parameter and its argument at all call sites. Nothing is added.
- **Benefit:** ~10 call sites lose a misleading argument; the function's real contract (theme file, else built-in) is what the signature says.
- **Effort:** S · **Risk:** Low (mechanical; no behaviour change — the value is provably unused) · **Confidence:** READ

### S-04 — The twelve-family theme roster is hand-copied in at least six places in one file
- **Category:** 2 (duplication)
- **Location:** `src/gfx/themes.cpp` — identical `theme_elems_t *groups[12]` arrays built independently at `:196-198` (`isFilteredDecoratorCoverImage`) and `:334-336` (`splitFilteredDecoratorCoverCaches`); `splitDecoratorCoverCache` calls `replaceSharedCoverCache` twelve times, once per family (`:313-324` region); `validateGUIElems` issues 56 explicit per-family calls across its validate/coverage/text-room/link/promote passes (`:533-652` region); `thmFree` frees twelve families by name; `thmSetColors` builds an `others[11]` array (`:1130-1134`) that is the same roster minus main, which is handled separately above it.
- **Problem + mechanism:** The roster of element families (main/info × games/apps/favs/vcd/favsVcd/favsApps) is a single logical list, but it has no single representation in this file. The favsVcd/favsApps families are the newest additions, and each one had to be threaded through every one of these enumerations by hand; the file's own comments record two bugs that were exactly a missed enumeration (a family the slot-based pass never reached, a decorator the split pass never recognised). The next family — or the next per-family pass — has the same six-plus chances to be silently skipped for one family, producing a page that alone loses its decorator split, its text rooms, or its recolour, with no compile error.
- **Fix (words):** One file-local helper/array that yields all twelve `theme_elems_t*` (with main flagged), consumed by the passes that treat families uniformly; the genuinely special cases (main's recolour, the fav-kind background rule) keep their explicit code and take the roster from the same source. This deletes five of the six copies; it adds no abstraction beyond the one table the file already rebuilds six times.
- **Justification if ADD:** The one shared roster array replaces six hand-maintained copies — net lines and net decision points both drop.
- **Benefit:** Adding a family or a per-family pass becomes a one-line roster change instead of a scavenger hunt; the class of "family X was missed by pass Y" bugs closes.
- **Effort:** M · **Risk:** Low–Medium (touches the theme-load path broadly; behaviour for the current twelve families is unchanged by construction, but wants a theme-switch bench pass) · **Confidence:** READ

### S-05 — `ConfigSet::clone` drops the set's on-disk format, silently breaking format inheritance for the clone
- **Category:** 6 (bugs/security) — inside the RIPTOPL-020 compat layer; the layer's existence is not re-filed, this is a defect within it
- **Location:** `src/core/config.cpp:330-344` (`ConfigSet::clone` copies type, filename, uid and every entry, then `dst->modified_ = 0;`) against `src/core/config.cpp:287` (`init` sets `format_ = CFG_FMT_LEGACY;`) and the write-side honouring of the format at `src/core/config.cpp:1588` (`if (configSet->format() == CFG_FMT_LIBCONFIG) cfgWriteLibconfig(...)`).
- **Problem + mechanism:** The config system's stated invariant (config.cpp's own header comments for the dual-format support) is *whatever format we read is the format we write back — we never convert a user's file*. `clone()` builds the destination through `create()`→`init()`, which resets `format_` to LEGACY, and never copies the source's `format_`. A clone of a set that was read from a wOPL/libconfig file therefore carries LEGACY, and if that clone is ever the set handed to `configWrite`, the file is rewritten in legacy syntax — the exact conversion the layer exists to prevent, destroying the file for wOPL. Verified containment today: the sole in-tree caller of `configClone` (grep, this round) is the test-launch path in `src/ui/guigame.cpp:2197`, whose comment states the clone is never persisted — so this is **latent**, not live. It is filed because the clone is a general API (`configClone` in `include/config.h`) whose contract comment says "deep copy", and format is part of the set's state everywhere except here.
- **Fix (words):** Copy `format_` in `clone()` alongside the entries (one assignment). Do not change the test-launch caller.
- **Benefit:** The deep-copy API actually copies the set's write-back semantics; the never-convert invariant stops depending on every future caller remembering not to save a clone.
- **Effort:** S · **Risk:** Low · **Confidence:** READ for the mechanism and for the sole-caller containment; INFERRED that no out-of-tree caller writes a clone

### S-06 — A libconfig group header whose name is too long leaves the *previous* group in force
- **Category:** 6 (bugs/security) — inside the RIPTOPL-020 compat layer (new defect, as S-05)
- **Location:** `src/core/config.cpp:825-840` — the group-header branch of `cfgReadLibconfigLine`: `if (klen > 0 && klen < groupSize) { memcpy(group, p, klen); group[klen] = '\0'; }` with no else, then `return;`.
- **Problem + mechanism:** When a group name meets or exceeds `groupSize` (CONFIG_KEY_NAME_LEN, 48), the branch silently does nothing and returns — crucially, it does **not** clear `group`. Every scalar that follows is then composed as `<previous-group>_<key>` (`"%s_%s", group, key` in the scalar branch) and stored under the wrong composed key. Compare the scalar branch of the same function, which refuses an over-long key outright ("never truncate into a hit"): the group branch's failure mode is worse than dropping the group — it actively mis-files the group's contents under whichever group came before (or, at file start, leaves them at root if `group` was empty, which is the only benign case). A hand-edited or third-party libconfig file with a long group name corrupts silently; no log line is emitted.
- **Fix (words):** On an unusable group header, clear `group` (and ideally log the malformed line, as the legacy reader does for malformed lines) so following scalars land at root rather than under a stale prefix.
- **Benefit:** A malformed foreign file degrades to root-level keys instead of silently re-homing a whole group's settings.
- **Effort:** S · **Risk:** Low · **Confidence:** READ

### S-07 — The config save's restore path writes the snapshot back with a single unchecked `write()` and logs success unconditionally
- **Category:** 6 (bugs/security)
- **Location:** `src/core/config.cpp:1677-1685` — inside `configWrite`'s failure path: `write(wfd, original, originalLen); close(wfd);` (both return values ignored), followed by `LOG("CONFIG write to %s FAILED -- restored %d original bytes\n", ...)` regardless of how many bytes were actually written.
- **Problem + mechanism:** This snapshot/restore machinery exists specifically for flaky devices — the surrounding comments describe a wedged HDD/MMCE emptying a good file via O_TRUNC and then failing the flush. The restore is the last line of defence on exactly that class of device, yet it issues one bare `write()` where the rest of this audit's files loop until completion (`favWriteWhole` in favsupport.cpp accumulates partial writes; `favWriteFile` then read-back-verifies). A partial restore `write()` — the expected failure shape on the device class that brought us here — leaves a truncated config on disk while the log asserts the full `originalLen` was restored, sending any later diagnosis in the wrong direction. The user-facing result is still an honest "save failed" (the function returns 0), so the harm is a silently half-restored file plus a false log claim, not a false success toast.
- **Fix (words):** Loop the restore write until the snapshot is fully written or an error occurs (the `favWriteWhole` pattern already in this codebase), check `close`, and log the byte count actually restored.
- **Benefit:** The anti-wipe guard either restores the whole file or says so honestly in the log.
- **Effort:** S · **Risk:** Low · **Confidence:** READ

### S-08 — `ConfigSet::getColor` reports success for a malformed colour value
- **Category:** 6 (bugs/security)
- **Location:** `src/core/config.cpp:437-445` — `getColor` calls `strToColor(valref, color); return 1;`, discarding the return value of `strToColor` (`src/core/config.cpp:36-63`), which returns 0 for a value not starting with `#` or containing a non-hex first character, after having zeroed the caller's 3-byte colour array.
- **Problem + mechanism:** Any present-but-malformed colour in a hand-edited config (e.g. `text_color=red`, or a value mangled by another tool) is reported to the caller as a successfully read colour of black (0,0,0) — or a partially parsed colour when the corruption is mid-string — instead of "no usable value", which is what callers need in order to keep their default. The parser already computes the failure; the getter throws it away.
- **Fix (words):** Return `strToColor`'s result from `getColor` (restoring the caller's colour on failure if any caller relies on the zeroing — the current zero-first behaviour is preserved either way by `strToColor` itself).
- **Benefit:** A corrupt colour value falls back to the caller's default instead of silently painting UI text black.
- **Effort:** S · **Risk:** Low · **Confidence:** READ (parser/getter mechanism); INFERRED that some callers treat a 0 return as "keep default" — that is the getter's contract everywhere else in this class (`getInt`/`getStr` return 0 on absence)

### S-09 — SMB share-picker trusts the IOP's share count against a 128-entry stack array
- **Category:** 6 (bugs/security)
- **Location:** `src/sources/ethsupport.cpp:828-858` — `ShareEntry_t sharelist[128];` on the stack, `getsharelist.maxent = 128;`, then `count = fileXioDevctl(..., SMB_DEVCTL_GETSHARELIST, ...)` and, for `count > 0`, `malloc(sizeof(base_game_info_t) * count)` and a population loop `for (i = 0; i < count; i++) { ... sharelist[i].ShareName ... }` with no clamp of `count` to 128.
- **Problem + mechanism:** `maxent` is a request to the driver; the EE side never verifies the reply honoured it. A driver (either SMB dialect — this path is shared) that returns a count above 128 makes the loop read `sharelist[i]` past the end of a stack array and publish that garbage as share names, and sizes the heap array from the same unchecked value. The codebase's own convention elsewhere is to clamp an external count at the EE boundary regardless of the producer's promise — favsupport.cpp caps a stored record count at FAV_MAX_ITEMS with the comment "never trust the stored count beyond the hard cap", and themes' listDir is passed an explicit remaining-slots bound. This site is the exception. (Not RIPTOPL-016: that finding covers the launch-leg credential `strcpy`s; this is the share-enumeration path.)
- **Fix (words):** Clamp `count` to the array's entry count (128) immediately after the devctl returns, before the allocation and the loop.
- **Benefit:** A mis-reporting driver degrades to a truncated share list instead of a stack out-of-bounds read in the share picker.
- **Effort:** S · **Risk:** Low · **Confidence:** READ for the missing clamp; INFERRED that a resident driver can return >maxent (no driver source was re-read for this section — the finding is the absent EE-side bound, per the codebase's own stated convention)

### S-10 — `FavSource::image` rescans the whole store from zero for every art request — the sibling lookup in the same file already has the fix
- **Category:** 5 (performance)
- **Location:** `src/sources/favsupport.cpp:1321-1408` (`FavSource::image`: linear scan from `i = 0`, calling `gsOf(o)->startup(o, fav->id)` per non-name-addressed entry; on an absolute-path miss it runs a **second** full scan in the passthrough loop) — contrast `src/sources/favsupport.cpp:919-960` (`FavSupport::artMode`), whose comment states: "All Games can hold thousands of rows and this runs for every art request, so search outward from the last match".
- **Problem + mechanism:** The neighbour-hint optimisation was applied to `artMode` — the *device-mode* lookup — but not to `image`, the lookup that actually fetches the art, although both are called per art request, both scan the same array, and `image`'s per-entry work is heavier (a `startup()` call into the owner support per row, plus a `vcdExtractGameId` fallback per PS1 row). On the All Games stops, where the store can hold thousands of rows, every cover request costs O(N) owner calls from the top of the list, and an attribute-image request that only the passthrough can satisfy costs O(2N). Covers near the end of a large All Games list pay the full scan every time; the rows asked about are, per artMode's own comment, almost always neighbours of the previous match.
- **Fix (words):** Give `image` the same outward-from-last-match search `artMode` already implements (share the hint member or replicate the pattern in this one function). No new structure; the pattern exists in the same file for the same array.
- **Benefit:** Per-cover cost on large Favourites/All Games lists drops from a full scan to a neighbourhood probe in the common sequential-browsing case.
- **Effort:** S · **Risk:** Low (search order changes only; the scan still covers every entry before answering -1) · **Confidence:** READ (structure and per-entry calls); the wall-clock saving is INFERRED — nothing was profiled, per this audit's no-hardware-claims rule

### S-11 — UDPFS theme discovery latches on a possibly partial root listing; its two sibling discovery functions refuse to
- **Category:** 6 (bugs/security)
- **Location:** `src/sources/udpfssupport.cpp:386-411` (`udpfsDiscoverThemes`: `while ((entry = readdir(root)) != NULL)` with no `errno` capture, then `if (!found) return; udpfsThemesScanned = 1;`) — contrast `src/sources/udpfssupport.cpp:424-455` (`udpfsDiscoverLanguages` captures `errno` around `readdir` and returns without latching `if (!found || failed || error)`) and `src/sources/udpfssupport.cpp:505-540` region (`udpfsDiscoverArtFolder`: `readError = errno; ... if (readError != 0) return; // an incomplete root listing must not become a permanent answer`).
- **Problem + mechanism:** The function's own header comment explains it scans for a THM folder **in any case** because an empty auto-created `THM` must not hide a populated `thm` beside it. But a `readdir` sequence that ends on a transient read error (UDPFS is a network filesystem; the server or link can drop mid-listing) is indistinguishable in this loop from a clean end-of-listing. If the first case-variant was already seen (`found = 1`) and a second, populated variant sat later in the listing, the function latches `udpfsThemesScanned = 1` for the whole session with only the empty variant registered — permanently reproducing, via a network hiccup, the exact "themes disappear for the session" failure the any-case scan was written to prevent. The languages and ART discovery functions in the same file were both written (or fixed) to treat a read error as "retry later, never latch"; themes is the one that was not.
- **Fix (words):** Capture `errno` around the `readdir` loop exactly as `udpfsDiscoverLanguages` does, and do not set `udpfsThemesScanned` when the listing ended in error.
- **Benefit:** A mid-listing network error costs one retry on the next poll instead of a session-long loss of a case-variant theme folder.
- **Effort:** S · **Risk:** Low · **Confidence:** READ
